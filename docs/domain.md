# ドメイン

**このアプリのドメインについては、この文書が唯一の正。** 用語・エンティティ・状態遷移・計算式で迷ったらここを見る。他の文書と食い違ったらこちらを取る。

守るべきルールそのものは `CLAUDE.md` の「絶対に守る不変条件」にある。**この文書はその背景と詳細**で、番号（不変条件1〜17）で相互に参照する。実装は `worker/src/domain/` にあり、**この文書と実装が食い違っていたら、それは直すべきバグ**（どちらが正かはその都度考える）。

## 1. このアプリが解く問題

**口座残高だけでは「本当に自由に使えるお金」が分からない。** 支払うと確定した支出が残高に残ったままだからである。ライブに行くと決めた時点でその金は自分のものではないが、引き落とされていないので残高には含まれている。実際より裕福に見える。

これを差し引いた**実質資産**を出すことが、このアプリの存在理由。あわせて、欲しいもの・やりたいこと・目標に対して**あといくら足りないか**と**あと何ヶ月で届くか**を出す。

## 2. 用語

コードのクラス名・テーブル名・API のキーは、すべてこの表に揃える（不変条件14）。

| 用語 | 実装名 | 定義 |
| --- | --- | --- |
| 口座 | `Account` | 資産を保持する入れ物。現金・預金または投資 |
| 口座残高 | `balance` | 口座が保持している金額。手動更新と、明細・定期入出金の適用で動く |
| 今ある額 | `cashTotal` | 現金・預金の合計。**画面の主役** |
| 実質資産（支払い後に残る額） | `NetAsset` | 今ある額 − 確定支出。**投資と貸借は含めない** |
| 見込み残高 | `ProjectedBalance` | 翌月1日時点の見込み。今ある額に定期入出金を足し引きする。**確定支出は含めない** |
| 確定支出 | `Commitment` | 支払うと確定しているがまだ払っていない金額。確定状態のウィッシュ |
| 投資資産 | `Investment` | 証券口座等の評価額。実質資産の外の参考値 |
| 貸借 | `Loan` | 誰かとの間で動いた、まだ精算していない金額。実質資産の外の参考値 |
| 向き | `LoanDirection` | 貸した (`lent`) か借りた (`borrowed`) か。**金額は向きによらず常に正** |
| 精算 | `settle` | 貸借の未精算残高を減らすこと。貸した側では回収、借りた側では返済 |
| 未精算 | `Outstanding` | `amount − settledAmount`。実質資産の外の参考値 |
| ウィッシュ | `Wish` | 欲しいもの・やりたいこと・目標。金額の見積を持つ |
| 不足額 | `Shortfall` | ウィッシュの金額 − 実質資産。負なら手が届く |
| 取引履歴 | `Transaction` | 口座残高が動いた記録。金額は符号付きで、出るときが負 |
| 入出金の明細 | `adjustment` | 手で打った取引履歴。**消せるのはこれだけ** |
| 定期入出金 | `RecurringEntry` | 毎月決まった日に口座を増減させるもの。給料・家賃 |
| 適用 | `apply` | 定期入出金をその月の分として実際に口座へ反映すること |
| 月次の集計 | `MonthlySummary` | 明細を月ごとに足し上げた収入・支出・余剰。**保存された行ではない** |
| 月間余剰 | `Surplus` | 月次収入 − 月次支出。負なら赤字 |
| 月次収支 | `MonthlyBalance` | 手入力の月次収支。**読み取り専用**（2026-08-01 に手入力を廃止） |

**言い換えない。** `TotalAsset` / `Remaining` / `Gap` / `Unpaid` のような別名を作ると、同じものが2つの名前で呼ばれ、grep が効かなくなる。

## 3. 中核の計算式

**この式がこのアプリの存在理由。** すべて `worker/src/domain/` の純粋関数として実装する。SQL に書かない（不変条件8）。

**口座の残高を3つの時点で出す。** どれも「現金・預金がいくらか」を別の時点で見たもの。

```
今ある額         = Σ(現金・預金の残高)

支払い後に残る額 = 今ある額 − Σ(確定状態のウィッシュの金額)   ← 実質資産
                   （このアプリの当初の目的。ただし画面の主役ではない）

見込み残高       = 今ある額 + Σ(翌月1日までに適用日が来る定期入出金)
                   （確定支出は含めない。いつ払うかが決まっていないため）

不足額(ウィッシュ) = ウィッシュの金額 − 実質資産

月間余剰(月) = その月の収入 − その月の支出

平均月間余剰 = 完了した直近3ヶ月の月間余剰の平均

到達見込み月数 = 不足額 ÷ 平均月間余剰            （切り上げ）

毎月いくら貯めればよいか = 不足額 ÷ (期限までの残り月数 + 1)  （切り上げ）

未精算(貸した) = Σ(lent の amount − settledAmount)
未精算(借りた) = Σ(borrowed の amount − settledAmount)
                  ↑ どちらも実質資産に足さない。差額にもまとめない
```

### 算出上の取り決め

- **不足額はウィッシュごとに独立して出す。** 合計金額との比較はしない（「A も B も買える」と出るが許容する）
- **平均に当月を含めない。** まだ終わっていない月を混ぜると、月初は家賃だけ引かれて給料がまだ、という状態になり、月の前半だけ余剰が過小に見える
- **平均に足すのは口座の入出金そのものだけ。** 手入力の明細（`adjustment`）と定期入出金の適用（`recurring_applied`）が該当し、ウィッシュの支払いと貸借の履歴は除く。臨時支出を余剰に混ぜると、**何か買うたびに他の目標の到達見込みが悪化する**
- **明細が1件も無い月に限り、手入力の月次収支で埋める。** 同じ月について両方は足さない（二重計上になる）
- **「算出不可」は 0 ではなく `null` で表す。** 平均月間余剰が 0 以下、完了した月のデータが 0 件、期限が過ぎている、などが該当する。0 として出すと「今月中に届く」「余剰なし」と読めてしまう
- **投資と貸借はどの式にも登場しない。** 参考値として別枠に表示するだけ
- **「今ある額」を主役にする。** 確定支出を引いた額だけを出していると「結局いまいくら持っているのか」が読めない。引き算をやめるのではなく、**引く前と引いた後の両方**を出す
- **見込み残高に確定支出を含めない。** いつ払うかが決まっていないため、含めると「まだ払っていないのに減っている」が別の形で再発する。未適用のまま残っている過去の定期は含める（適用日が来ている＝起きているはずのこと）

## 4. エンティティ

属性は代表的なものだけを挙げる。正確なシグネチャは `worker/src/domain/` を見ること。

### Account（口座）

| 属性 | 備考 |
| --- | --- |
| `kind` | `cash` / `investment`。**生成後に変更できない**（不変条件1） |
| `balance` | 手動更新と、明細・定期入出金の適用で動く |
| `updatedAt` | 残高がいつ時点のものか。`isStale()` の判断材料 |

持っている判断：`countsTowardNetAsset()`（`cash` のみ true）、`isStale()`。

**`kind` を変えられない理由。** `cash` → `investment` に書き換わると、その口座が実質資産から丸ごと消える。API も SQL も種別を書ける経路を持たない。

### Loan（貸借）

| 属性 | 備考 |
| --- | --- |
| `direction` | `lent` / `borrowed`。**向きはこの項目だけが表す** |
| `amount` | **向きによらず常に正** |
| `settledAmount` | 精算済みの額。部分精算に対応 |

持っている判断：`outstanding()`、`status()`（未精算 / 一部精算 / 精算済み）、`settle()`。

**向きを金額の符号で表さない理由。** 負の金額で「借りた」を表すと、`amount > 0` の検査が借りた側に効かなくなり、金額の妥当性と向きの判定が絡み合う。向きを独立させれば、検査は両方向に同じまま効く。

**貸借は口座残高を動かさない**（不変条件4）。カードで立て替えた場合、現金はまだ出ていない。「立て替えた ＝ 現金が出た」と決め打ちできない。

### Wish（ウィッシュ）

| 属性 | 備考 |
| --- | --- |
| `status` | `considering` / `committed` / `done` / `dropped` |
| `amount` | 検討中は見積、確定後は確定額 |
| `deadline` | 任意。あれば「毎月いくら貯めればよいか」が出せる |

持っている判断：`isCommitment()`（`committed` のみ true）、`commit()` / `pay()` / `drop()`。

**ライブや旅行も、確定前はウィッシュとして登録される。** 別のエンティティにしないのは、両者のライフサイクルが同一のため。

### Transaction（取引履歴）

| 属性 | 備考 |
| --- | --- |
| `amount` | **符号付き。** 口座から出るときが負 |
| `kind` | 下の表を参照 |
| `refId` | 参照先。`adjustment` のときだけ `null` |
| `note` | 覚書。**分類（カテゴリ）は持たない** |

種別と、それぞれに許されること：

| `kind` | 作られる経路 | 消せる | 月次に足す | メモを持つ |
| --- | --- | --- | --- | --- |
| `adjustment` | 手で打つ | ○ | ○ | ○ |
| `recurring_applied` | 定期入出金の適用 | ✕ | ○ | ○ |
| `wish_paid` | ウィッシュの支払い | ✕ | ✕ | ✕ |
| `lending_created` / `lending_collected` | **もう作られない**（2026-07-30 より前の履歴） | ✕ | ✕ | ✕ |

軸が2つあることに注意する。

- **消せるか** = `isManualEntry()`。手で打ったものだけ。他は対になる記録（ウィッシュの状態、適用済み年月）と食い違うため消せない
- **月次に足すか** = `countsTowardMonthlySummary()`。口座の入出金そのものを表すもの（`isCashFlowKind`）だけ

**この2つを1つの軸で判断しない。** `recurring_applied` は参照先を持つが月次には足す、という組み合わせが存在する。

### RecurringEntry（定期入出金）

| 属性 | 備考 |
| --- | --- |
| `amount` | **符号付き。** 給料は正、家賃は負。明細と同じ約束 |
| `dayOfMonth` | 1〜31。月末の無い月は**その月の末日に丸める** |
| `appliedThrough` | この年月までは適用済み。次はこの翌月から |

持っている判断：`dueDateIn()`、`pendingMonths()`、`markAppliedThrough()`。

**`appliedThrough` を `null` にしない。** 「まだ一度も適用していない」を null で表さず、登録時に**登録月の前月**を入れる。未適用月の算出が常に「翌月から」になり、場合分けが消える。「起点は当月」という決定が値そのもので表現される。

**適用は自動では起きない。** 開いたときに件数を出し、押したときだけ残高が動く。背景で勝手に動かない分、何が起きたかが常に見える。

### MonthlySummary（月次の集計）

明細を月ごとに足し上げた導出値。**ID を持たない**（不変条件12）。保存された行ではないので、ID を付けると更新できるように見える。

`source` が `entries`（明細の集計）か `manual`（明細が1件も無い月を手入力で埋めた）かを持つ。**どちらを見ているかが画面から読めないと、「明細を打ったのに反映されない」ように見える。**

## 5. 状態遷移

### Wish

```
  ┌─────────┐   commit    ┌────────┐    pay     ┌────────┐
  │ 検討中  │ ──────────▶ │  確定  │ ─────────▶ │  完了  │
  └─────────┘             └────────┘            └────────┘
       │ drop                  │ drop
       ▼                       ▼
  ┌─────────┐             ┌─────────┐
  │ 見送り  │             │ 見送り  │
  └─────────┘             └─────────┘
```

| From \ To | considering | committed | done | dropped |
| --- | --- | --- | --- | --- |
| considering | — | `commit` | ✕ | `drop` |
| committed | ✕ | — | `pay` | `drop` |
| done | ✕ | ✕ | — | ✕ |
| dropped | ✕ | ✕ | ✕ | — |

`done` と `dropped` は終端。取り消しはしない（誤操作は削除して作り直す）。

各状態が実質資産に与える影響：

| 状態 | 実質資産 | 説明 |
| --- | --- | --- |
| 検討中 | 影響なし | まだ意思決定に入っていない |
| **確定** | **控除される** | 払うと決めた時点で自分の金ではない |
| 完了 | 影響なし（残高が実際に減る） | 支払い時に取引履歴が作られる |
| 見送り | 影響なし | |

**支払いの前後で実質資産は変わらない。** 確定支出から外れると同時に、同額だけ残高が減る。これが正しい挙動になる。

### Loan

```
未精算 ─(一部精算)─▶ 一部精算 ─(残額精算)─▶ 精算済み
   └────────────(全額精算)──────────────────┘
```

向きによらず同じ。**精算の経路を向きごとに分けない。** 処理はどちらも「未精算残高が減る」だけなので、分けると同じ手順が2本に増える。

### RecurringEntry の適用

```
applied_through = 2026-06
      │
      │ apply（2026-08-25 に実行、適用日が毎月25日なら）
      ▼
applied_through = 2026-08   ＋ 2026-07-25 と 2026-08-25 の履歴2件 ＋ 残高が2ヶ月分動く
```

**巻き戻せない。** 同じ月を二度適用する経路ができると、残高が二重に動く。

## 6. ドメインエラー

業務ルール違反は `DomainError` として投げ、handler が **422** に対応させる（不変条件13）。形式の誤り（400）と区別する。

現在のコード一覧は `worker/src/domain/errors.ts` の `DOMAIN_ERROR_MESSAGES` にある。**新しい業務ルールを足すときは、まずここにコードを定義する。** handler で個別に 422 を投げない。

## 7. やらないこと

以下はドメインに入れない。要望が出ても、まずここを読む。

| 項目 | 理由 |
| --- | --- |
| 支出の分類（カテゴリ）と分類別集計 | 家計簿になる。「何に使ったか」はメモで足りる |
| 銀行 API 連携・レシート読み取り | 契約面で現実的でない／目的外 |
| 複数ユーザー・共有 | 単一ユーザー（作者本人）専用 |
| 外貨・為替 | 日本円のみ。金額は円単位の整数 |
| 確定支出の分割払い | 金額は一括で扱う |
| ウィッシュの合計金額と実質資産の比較 | 個別に見る方針で確定済み |
