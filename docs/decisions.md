### 2.1 投資欄を消す／期限までに毎月いくら

**投資資産の表示をやめた。** 実質資産に含めない値（不変条件1）なので、そもそも見たい値ではなかった。API とスキーマはそのままなので、戻したくなったら front を1箇所直すだけ。

**`monthlySavingNeeded` を追加した。** 既存の `monthsToReach`（この余剰なら何ヶ月かかるか）と逆向きの計算で、期限が決まっているウィッシュに対して「毎月いくら積めば間に合うか」を出す。

決めた点：

- **残り月数に当月を含める。** 期限が当月なら「今月中に全額」の意味。0ヶ月で割ると無限大になるうえ、「今月が期限」は「もう間に合わない」ではない
- **期限が過ぎていれば `null`。** 0 を返すと達成済みに見える
- **平均月間余剰に依存しない。** 月次収支が未登録でも、期限さえあれば出せる

### 2.2a 立替を口座から切り離す

#### 何が問題だったか

**カードで立て替えた分が、まだ引き落とされていないのに残高から引かれる。**

現行は「立て替えた ＝ 現金が出た」と決め打ちしている。現金で立て替えた場合はこれで正しく、残高が減って未回収が増え、**実質資産は変わらない**（＝アプリの主張そのもの）。しかしカード払いだと、現金はまだ出ていないのに減らしてしまう。

#### 決めたこと

**立替を実質資産の計算から外し、別枠の参考値として表示する。** いま投資資産がそうなっているのと同じ扱いにする。

- 立替を登録しても口座残高は動かない
- 未回収分は実質資産に足さない
- ダッシュボードに「未回収の立替 12,000円」と別枠で出す

#### これは何を変えたか

**要件定義書を v1.1 にし、1.1「課題」・1.2「目的」・3章の計算式を書き換えた。** アプリの存在理由の半分がここにあったが、**実際に使った結果「立替は別に見えればいい」という結論が出た。** 使う前の想定より、使った後の実感を優先する。

不変条件4を書き換えた。1と10はそのまま。

| 番号 | 変更 |
| --- | --- |
| 1 | そのまま |
| 4 | 「未回収残高は `amount - collected_amount`」に加えて、**実質資産に加算しない／口座残高を動かさない／取引履歴を作らない**を明記した |
| 10 | 仕組みは残す。立替の書き込みが1行になっても `AtomicWriter` を通しているのは、回収に楽観ロックが要るため（下記） |

#### 着手時に決めたこと

**未回収額を `breakdown` に残さず、`Dashboard` の別フィールドにした。**

当初の計画では「`netAsset()` から外し、`breakdown` には表示用に残す」と書いていた。**これは採らなかった。** `netAsset(b)` が `b` の一部のフィールドを意図的に無視する形になり、「内訳にあるのに合計に入っていない項目」ができる。あとから誰かが（あるいは自分が）足し戻す事故が起きうる。

`NetAssetBreakdown` を `{ cashTotal, commitments }` だけにして **`netAsset()` が全フィールドを必ず使う形**を保ち、未回収額は `investmentTotal` と並ぶ参考値のフィールドにした。JSON の形も同じで、`breakdown` の外に出ている。**合計に足されない値を内訳に混ぜない、を構造で示す。**

**既存データの残高は補正しない。** 本番にはすでに、立替の登録で残高が減った状態のデータが入っている。マイグレーションで足し戻すことはしない。残高はもともと手動入力（要件定義書 2.3）で、次に残高を打ち直した時点で正しくなる。**マイグレーションで金額を動かすと、間違えたときに何が起きたのか追えなくなる。**

`transactions` に残っている `lending_created` / `lending_collected` の行と、`kind` の CHECK 制約はそのまま残した。過去の履歴として読めるほうがよい。新しく作られることはない。

**回収日を受け取らなくした。** 以前は取引履歴の `occurred_on` に入れていたが、口座を触らなくなった今それは作られない。`lendings` に回収日を持つカラムは無い。使わない引数を残すと「日付を渡したのに残らない」ことになるため、API から外した（送れば 400）。

#### 実装した範囲

- `domain/netAsset.ts`：`calculateBreakdown` が立替を引数に取らなくなった。`calculateOutstandingLendings` を追加（2b で `calculateOutstandingLoans` に改名）
- `usecase/lending.ts`：`create` / `collect` が口座も取引履歴も触らない。`AccountRepository` と `Clock` の注入も不要になった
- `usecase/dashboard.ts`：`Dashboard` に `outstandingLendings` を追加
- `handler`：`POST /api/lendings` から `accountId`、`/collect` から `accountId` と `occurredOn` が消えた
- `front`：立替画面から口座選択を外し、ダッシュボードに参考値の欄を追加
- **マイグレーションは無し。** スキーマは変わっていない

**2a では名前を変えていない。** `Lending` / `lendings` / `collect` のまま口座から切り離した。改名は 2b にまとめた。

### 2.2b 貸す・借りるの両方を登録できるようにする

#### 何が問題だったか

**借りた金を登録する場所が無かった。** 貸した分（立替）しか扱えず、借りている額は把握できなかった。口座から切り離した（2a）ことで、向きを分けるだけで済むようになった。

#### 決めたこと

**用語を作り直した。** `Lending`（立替）という名前が「借りた金」も指すことになり、不変条件14（設計書の用語をそのままコードの名前に使う）と噛み合わなくなる。上位語の**貸借（Loan）**を要件定義書の用語定義に足し、**クラス名・テーブル名・カラム名・API 経路・画面の文言まで揃えて改名した。**

| 変更前 | 変更後 |
| --- | --- |
| `Lending` / `lendings` テーブル | `Loan` / `loans` テーブル |
| `collected_amount` / `collectedAmount` | `settled_amount` / `settledAmount` |
| `collect()` / `POST /api/lendings/{id}/collect` | `settle()` / `POST /api/loans/{id}/settle` |
| `CollectionStatus`（`uncollected` / `collected`） | `SettlementStatus`（`unsettled` / `settled`） |
| `COLLECT_EXCEEDS_OUTSTANDING` | `SETTLE_EXCEEDS_OUTSTANDING` |
| 「回収」 | 「精算」（貸した側では回収、借りた側では返済） |

差分は大きいが、**名前と概念がずれたまま増築するほうが高くつく。**

#### 着手時に決めたこと

**向きは `direction` カラムで持ち、金額の符号では表さない。**

負の金額で「借りた」を表すと、`amount > 0` の CHECK が借りた側に効かなくなり、金額の妥当性と向きの判定が絡み合う。向きを独立させれば、検査は両方向に同じまま効く。domain の `Loan.amount` も向きによらず常に正。

**精算の経路を向きごとに分けない。** `/collect` と `/repay` に割る案も検討したが採らなかった。domain の処理はどちらも「未精算残高が減る」だけで同一なので、分けると同じ手順が2本に増える。さらに「`lent` に `/repay` を投げたら 422 か」という判定が新たに必要になる。**画面の文言だけを向きで変え、処理は1本にした。**

**ダッシュボードは貸しと借りを2行で出す。** 差額（貸し 12,000 − 借り 5,000 = 7,000）に丸めると、誰にいくら貸しているのかが消える。API も `outstandingLent` / `outstandingBorrowed` に分けて返す。片方が0でも行は消さない（消えると「借りている分は無い」ことが分からない）。

**マイグレーションはテーブルを作り直す形にした。** `ALTER TABLE ... RENAME` でも中身は移せるが、**名前付き CHECK 制約の名前は変わらない。** `lendings_collected_within_amount` が `loans` に残り、違反時のエラーに旧名が出続ける。制約名を変えるにはどうせ作り直しが要る。件数は年間数百件なのでコストは問題にならない。

**既存行の `direction` はすべて `'lent'`。** 変更前は貸した分しか登録できなかったので、既存行は貸した側で確定している。

#### 実装した範囲

- `migrations/0002_loans.sql`：`loans` を作り直し、`lendings` から全行を移して `DROP`
- `domain/loan.ts`：`Loan` / `LoanDirection` / `SettlementStatus`。`settle()` は向きで分岐しない
- `domain/netAsset.ts`：`calculateOutstandingLoans` が `{ lent, borrowed }` を返す
- `handler`：`/api/loans`、`/settle`、`direction` の受け取り（妥当性は domain が判定するので 422）
- `front`：登録フォームに向きの select、一覧に向きのラベル、ダッシュボードに2行

#### 残っている論点

**相手別の合計を出すかは未決。** 要件定義書 F-05 には「相手別の合計表示」があったが、実装していない。件数が増えたら考える。

### 2.3 入出金の明細を打てるようにする

#### 何が問題だったか

**支出を月単位でしか記録できなかった。**

> paypayに送金したとか、カードの費用とか、項目別にやりたい。月でこうだったって一括でやるよりも肌感に合ってる

#### 決めたこと

**1件ずつ「金額・日付・メモ」を打つ。分類（カテゴリ）は持たない。**

分類を持たないので、`CLAUDE.md`「やらないこと」の**家計簿化には踏み込まない**。「何に使ったか」はメモを読めば分かる。分類を入れると、次に来るのは分類別の集計で、そこまで行くとこのアプリは実質資産を見る道具ではなくなる。

**明細を打つと口座残高が動く。** 貸し借り（2a で口座から切り離した）とはここが逆。実際に金が動いた記録なので、動かさないほうが不自然になる。

#### 着手時に決めたこと

**削除では残高も戻す。** 打ち消しの明細を足す方式（赤伝）と、履歴だけ消す方式も検討した。

| 案 | 判断 |
| --- | --- |
| 削除で残高も戻す | **採用。** 打ち間違いは消せるのが個人アプリの肌感に合う |
| 打ち消しの明細を足す | 採らない。打ち間違いが一覧に残り続け、1件の誤りが2行に増える |
| 履歴だけ消す | 採らない。残高と履歴がずれ、「残高の裏付けを辿る」という履歴の存在理由が壊れる |

**消せるのは手入力の明細だけ。** ウィッシュの支払いのように参照先を持つ履歴には対になる記録がある。履歴だけ消して残高を戻すと、ウィッシュが完了のままなのに支払いが無かったことになる。判定は `Transaction.ensureDeletable()` に置き、usecase に `if (kind === 'adjustment')` を書かない（不変条件6）。違反は 422。

**二重に戻る心配は要らない。** 削除は残高の更新と同じ batch に載り、残高が楽観ロックの番人を兼ねる。2つのタブから同じ明細を消すと、2度目は 409 になる。

**金額は符号付きで受ける。** 貸し借りは `direction` を別に持つが、こちらは符号1本にした。`Transaction.amount` はもともと「口座から出るときは負」で確定しており、一覧も符号付きで返している。入口だけ形を変えると、同じ値の表現が2つになる。画面のフォームは入金／出金の select を持ち、送る直前に符号を付ける。**front がしているのは向きの表し方をサーバーに合わせることだけで、金額の計算はしていない。**

**`kind` は既存の `adjustment` を再利用した。** 「残高の手動調整」のつもりで置いていたが、作る経路が無く1件も存在しなかった。新しい種別を足すと、実体の無い種別が2つ並ぶ。ラベルを「入出金」に直し、意味を与えた。4番の集計では `kind = 'adjustment'` だけを足せばよい。

#### 実装した範囲

- `migrations/0003_transaction_note.sql`：`transactions` に `note TEXT NOT NULL DEFAULT ''` を追加。**テーブルの作り直しではなく `ALTER`。** 制約名も列名も変えないので、0002 のような事情が無い
- `domain/transaction.ts`：`note` と `ensureDeletable()`。参照先を持つ種別ではメモを落とす（参照先の扱いと同じ）
- `usecase/transaction.ts`：`create` / `delete`。どちらも口座残高の増減と同じ `WriteOperation` の配列に載せる
- `port.ts`：`WriteOperation` に `deleteTransaction` を追加。`TransactionRepository` に `get` を追加。**作成と削除はリポジトリに置かない。** 単独で書ける経路を残すと、履歴だけが増えて残高が動かない状態を作れる
- `handler`：`POST /api/transactions`、`DELETE /api/transactions/{id}`
- `front`：「入出金」画面を追加（画面は6つになった）。一覧・登録・削除

#### 残っている論点

**口座の残高を直接打ち直す経路（`PATCH /api/accounts/{id}`）が残っている。** 明細を打つ経路と併存しており、そちらで動かした分は明細に出ない。4番で明細から月次を集計するとき、この差が効いてくる。**4に着手する時点で、残高の直接編集を残すかを決める。**

---

### 2.4 月次収支を明細から自動集計

#### 何が問題だったか

**同じ数字を2回入れることになっていた。** 3本目で明細を打てるようにした結果、月次収支の手入力と明細が併存し、どちらが正なのかが決まらなくなった。

#### 決めたこと

**月次収支の手入力をやめ、明細を足し上げて「その月の収入・支出」を出す。** 入力が1本化される。`PUT /api/monthly-balances/{yearMonth}` と登録フォームは廃止し、`GET /api/monthly-summaries` に置き換えた。

#### 着手時に決めたこと

**当月は平均月間余剰に含めない。** まだ終わっていない月を混ぜると、余剰が実態より小さく見える。月初なら家賃だけ引かれて給料がまだ、という状態になり、**月の前半だけ到達見込みが悪化する。** 判定は `averageSurplus` の中に入れた。呼ぶ側が当月を除いてから渡す形にすると、除き忘れられる。

**足すのは手入力の明細（`adjustment`）だけ。** ウィッシュの支払いと、過去の貸し借りの履歴は除く。ライブ代のような臨時支出を月の余剰に混ぜると、**何か買うたびに他の目標の到達見込みが悪化する。** 生活費とウィッシュ由来の支出を分けるという不変条件2の考え方を、集計にも引き継いだ。判定は `Transaction.isManualEntry()` が持つ。

**明細が1件も無い月だけ、手入力の値で埋める。** 3案を比べた。

| 案 | 判断 |
| --- | --- |
| 明細が無い月だけ手入力で埋める | **採用。** 乗り換えた直後に到達見込みが算出不可へ落ちない |
| `monthly_balances` ごと廃止 | 採らない。真実は1つになるが、**明細が3ヶ月分貯まるまで到達見込みが出せない** |
| 読み取り専用で残すが集計には使わない | 採らない。過去は見られるが、計算上は廃止と同じ |

**月単位でどちらか一方に決める。** 同じ月について両方を足すと二重計上になる。明細が1件でもあればその月は明細が正で、手入力の値は使わない。**どちらを見ているかは `source`（`entries` / `manual`）で返し、画面にもバッジで出す。** 示さないと「明細を打ったのに反映されない」ように見える。

**`monthly_balances` の表は残し、書き込む文を消した。** `D1MonthlyBalanceRepository` から `upsert` を削除し、リポジトリのインターフェースも `listAll` だけにした。**SQL に無い操作は、上の層がどう間違えても起こせない**（`CLAUDE.md` の設計方針）。テストで過去の月を再現するときは、テスト専用のヘルパ（`givenMonthlyBalance`）から直に入れる。

**マイグレーションは無し。** 表も列も変えていない。

#### 実装した範囲

- `domain/monthlySummary.ts`：`MonthlySummary` と `summarizeMonths`。**ID を持たない**（導出値であって保存された行ではない。不変条件12）
- `domain/transaction.ts`：`isManualEntry()`。`ensureDeletable()` もこれを使う形に寄せた
- `domain/netAsset.ts`：`averageSurplus` が当月を除き、`MonthlyFigures`（月間余剰を持つもの）を受け取るようになった
- `usecase/monthlySummary.ts`：`MonthlyBalanceUsecase` を置き換え。`usecase/dashboard.ts` も明細から平均を出す
- `handler`：`GET /api/monthly-summaries`。`monthly-balances` の2経路は消した（叩けば 404）
- `front`：`MonthlySummaries` 画面（入力欄なし、手入力の月にバッジ）

#### 残っている論点

**口座残高の直接編集（`PATCH /api/accounts/{id}`）は残したまま。** 3本目で挙げた論点だが、今回は触っていない。残高の打ち直しは明細に出ないので、その分は月次の集計にも表れない。**これは「残高は手動入力」という要件定義書 2.3 の前提と、明細で積み上げる新しい形が併存している状態。** 5本目（定期入出金）でも同じ問題に触れるので、そこで決める。

### 2.5 定期入出金（給料・家賃）

#### 何が問題だったか

**毎月同じ額が動くものを都度打つのは手間で、打ち忘れると残高がずれる。**

#### 決めたこと

**符号付きの定期入出金を登録し、指定日に口座へ ± する。** 給料 `+250,000`、家賃 `-80,000` のように、収入と支出を1つのテーブルで扱う。

**適用はアプリを開いたときにまとめて行う。** Cron Trigger は使わない。

| | |
| --- | --- |
| 選んだ理由 | 背景で勝手に動かない分、何が起きたかが常に見える。失敗しても画面で分かる |
| 2ヶ月開かなかったら | 開いた時点で2ヶ月分をまとめて適用する。これが正しい挙動 |
| 二重適用の防止 | 「どこまで適用したか」を記録する。Cron を使う場合も同じ仕組みが要る |

**開いただけでは適用しない。** ダッシュボードに「2件（合計 ¥170,000）が未適用です」と出し、**押したときだけ**残高が動く。画面を開いた副作用で金が動くと、何が起きたのか後から分からなくなる。

#### 着手時に決めたこと

**適用の履歴に専用の種別 `recurring_applied` を足した。** `adjustment`（手入力の明細）の再利用も検討したが採らなかった。

| | `recurring_applied`（採用） | `adjustment` の再利用 |
| --- | --- | --- |
| 由来 | `ref_id` から定期入出金を辿れる | 手入力と見分けがつかない |
| 削除 | 不可（422）。適用済み年月と食い違うため | 可能。消しても再適用されず、記録と食い違う |
| 月次の集計 | 足す | 足す |
| コスト | `transactions` の作り直しが要る | 不要 |

**この結果、「参照先を持つ ＝ 月次に足さない」という 3・4本目の前提が崩れた。** `recurring_applied` は参照先を持つが、生活費の収支そのものなので月次には足す。判定を「口座の入出金そのものを表す種別か」（`isCashFlowKind`）として切り出し、削除可否（`isManualEntry`）とは別の軸にした。**メモを持てるのも同じ軸。** 適用時に定期入出金の名称を写しておくと、定期のほうを消しても履歴が読める。

**`applied_through` を NULL にしない。** 「まだ一度も適用していない」を null で表さず、登録時に**登録月の前月**を入れる。未適用月の算出が常に「翌月から」になり、場合分けが消える。**「起点は当月」という決定が、値そのもので表現される。**

**月末の無い月は末日に丸める。** 31日を指定した2月は2月28日（閏年なら29日）に適用する。翌月に送ると、2月分が3月1日に入って「2月は適用されていない」ように見える。丸めは domain が行い、SQL には持たせない。

**同じ口座への増減は1本の UPDATE にまとめる。** 給料と家賃が同じ口座なら、2本並べると2本目の「読み取り時の残高」が1本目の適用後の値と食い違い、番人（楽観ロック）が必ず失敗する。増減を先に合算してから1本にする。適用済み年月も同様に、最後の月まで一度に進める。

**`transactions` を作り直した。** SQLite は CHECK 制約を後から足せない。0002 で `loans` を作り直したのと同じ事情。

**一度に適用するのは12ヶ月分まで。** 日付が壊れた値だったときに無限に回さないための上限。それを超えて開かなかった分は、必要なら明細で手当てする。

#### 実装した範囲

- `migrations/0004_recurring_entries.sql`：`recurring_entries` の追加と `transactions` の作り直し
- `domain/recurring.ts`：`RecurringEntry`、`pendingApplications`、`pendingTotal`。**未適用月の算出は純粋関数**（不変条件8）
- `domain/yearMonth.ts`：`daysInMonth()`。`Date` を使わず閏年を判定する（domain にタイムゾーンを持ち込まない）
- `domain/transaction.ts`：`isCashFlowKind` / `countsTowardMonthlySummary()`。削除可否とは別の軸に分けた
- `usecase/recurring.ts`：`create` / `pending` / `apply` / `delete`
- `handler`：4経路。ダッシュボードに `pendingRecurringCount` / `pendingRecurringTotal`
- `front`：「定期」画面と、ダッシュボードの適用ボタン（画面は7つになった）

#### 残っている論点

**口座残高の直接編集（`PATCH /api/accounts/{id}`）は残したまま。** 3・4本目からの持ち越しで、今回「残す」と決めた。実際の口座と突き合わせてズレを直す手段が要るため。ただし**打ち直した分は明細に出ないので、月次の集計にも表れない**という性質は残る。

**定期入出金の内容は編集できない。** 金額や適用日を直したいときは消して作り直す。適用のついでに条件が変わると、「どの条件で適用されたか」と履歴が食い違うため、書ける文を置かなかった。件数が少ないので当面はこれで足りる。
