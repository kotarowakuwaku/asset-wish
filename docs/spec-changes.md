## 1. 投資欄を消す／期限までに毎月いくら（完了）

**投資資産の表示をやめた。** 実質資産に含めない値（不変条件1）なので、そもそも見たい値ではなかった。API とスキーマはそのままなので、戻したくなったら front を1箇所直すだけ。

**`monthlySavingNeeded` を追加した。** 既存の `monthsToReach`（この余剰なら何ヶ月かかるか）と逆向きの計算で、期限が決まっているウィッシュに対して「毎月いくら積めば間に合うか」を出す。

決めた点：

- **残り月数に当月を含める。** 期限が当月なら「今月中に全額」の意味。0ヶ月で割ると無限大になるうえ、「今月が期限」は「もう間に合わない」ではない
- **期限が過ぎていれば `null`。** 0 を返すと達成済みに見える
- **平均月間余剰に依存しない。** 月次収支が未登録でも、期限さえあれば出せる

## 2. 立替を口座から切り離す

### 何が問題だったか

**カードで立て替えた分が、まだ引き落とされていないのに残高から引かれる。**

現行は「立て替えた ＝ 現金が出た」と決め打ちしている。現金で立て替えた場合はこれで正しく、残高が減って未回収が増え、**実質資産は変わらない**（＝アプリの主張そのもの）。しかしカード払いだと、現金はまだ出ていないのに減らしてしまう。

### 決めたこと

**立替を実質資産の計算から外し、別枠の参考値として表示する。** いま投資資産がそうなっているのと同じ扱いにする。

- 立替を登録しても口座残高は動かない
- 未回収分は実質資産に足さない
- ダッシュボードに「未回収の立替 +12,000円」と小さく出す

あわせて**貸す／借りるの両方**を登録できるようにする。口座から切り離すため、符号を分けるだけで済む。

### これは何を変えるか

**要件定義書 1.2「立替を加味した実質資産」を書き換える。** アプリの存在理由の半分がここにあったが、**実際に使った結果「立替は別に見えればいい」という結論が出た。** 使う前の想定より、使った後の実感を優先する。

不変条件も見直す。

| 番号 | 現状 | 見直しの方向 |
| --- | --- | --- |
| 1 | 実質資産に investment を含めない | そのまま |
| 4 | 未回収残高は `amount - collected_amount` | 計算は残る（表示に使う）。実質資産への加算だけをやめる |
| 10 | 書き込みの原子性は usecase が決める | 立替が口座を触らなくなるため、原子的な書き込みはウィッシュの支払いだけになる。仕組みは残す（3・5で再び要る） |

### 実装の見当

- `migrations/0002`：`lendings` に `direction`（`'lent'` / `'borrowed'`）を追加
- `domain/netAsset.ts`：`netAsset()` から `outstandingLendings` を外す。`breakdown` には残す（表示用）
- `usecase/lending.ts`：`create` / `collect` が口座も取引履歴も触らなくなる。`accountId` が不要になる
- `handler`：立替の API から `accountId` が消える
- `front`：立替画面から口座選択を外す。ダッシュボードに参考値を出す

## 3. 入出金の明細を打てるようにする

### 決めたこと

**1件ずつ「金額・日付・メモ」を打つ。分類（カテゴリ）は持たない。**

> paypayに送金したとか、カードの費用とか、項目別にやりたい。月でこうだったって一括でやるよりも肌感に合ってる

分類を持たないので、`CLAUDE.md`「やらないこと」の**家計簿化には踏み込まない**。「何に使ったか」はメモを読めば分かる。

### 実装の見当

- `migrations/0002`：`transactions` に `note TEXT NOT NULL DEFAULT ''` を追加
- `POST /api/transactions` / `DELETE /api/transactions/{id}`
- 口座残高の更新と履歴の記録は原子的に行う（既存の `AtomicWriter` をそのまま使う）
- 種別は既存の `adjustment` を使う。domain は既に対応済み

## 4. 月次収支を明細から自動集計

### 決めたこと

**月次収支の手入力をやめ、明細を足し上げて「その月の収入・支出」を出す。** 入力が1本化される。

`monthly_balances` テーブルと関連する画面・API は廃止になる見込み。

### 着手前に決めること（未決）

**当月をどう扱うか。** まだ終わっていない月を平均に含めると、余剰が過小に見える（月初なら支出だけ計上済みで収入がまだ、など）。**完了した直近3ヶ月だけを使う**のが素直だと思われるが未確定。

**ウィッシュの支払いを平均余剰に含めるか。** ライブ代のような臨時支出を余剰に混ぜると、買うたびに他の目標の到達見込みが悪化する。**`wish_paid` は平均から除く**のが、不変条件2（生活費とウィッシュ由来の支出を分ける）の精神を引き継ぐ形。

この2つは4に着手する時点で確定させる。

## 5. 定期入出金（給料・家賃）

### 決めたこと

**符号付きの定期入出金を登録し、指定日に口座へ ± する。** 給料 `+250,000`、家賃 `-80,000` のように、収入と支出を1つのテーブルで扱う。

**適用はアプリを開いたときにまとめて行う。** Cron Trigger は使わない。

| | |
| --- | --- |
| 選んだ理由 | 背景で勝手に動かない分、何が起きたかが常に見える。失敗しても画面で分かる |
| 2ヶ月開かなかったら | 開いた時点で2ヶ月分をまとめて適用する。これが正しい挙動 |
| 二重適用の防止 | 「どこまで適用したか」を記録する。Cron を使う場合も同じ仕組みが要る |

### 実装の見当

- `recurring_entries` テーブル（名称・符号付き金額・口座・適用日・最終適用年月）
- ダッシュボードで未適用を検出し、「2件適用しますか？」と出す
- 適用は口座残高の更新と履歴の記録を原子的に行う
