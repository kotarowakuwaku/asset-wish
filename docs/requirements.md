## 1. 背景と目的

### 1.1 課題

口座残高を見ても「本当に自由に使えるお金」が分からない。**支払うと確定している支出が残高に残っている**ためである。ライブや旅行に行くと決めた時点でそのお金は自分のものではないが、まだ引き落とされていないため残高には含まれている。実際より裕福に見える。

また、欲しいものや将来の大きな買い物に対して「あといくら足りないのか」が把握できておらず、判断ができない。

**立替金について（1.1 で変更）。** 1.0 では「他人のために立て替えた金額が残高から抜けているため実際より貧乏に見える」ことを2つ目の課題としていた。**これは実際に使ってみて成立しないことが分かった。** 現金で立て替えた場合はその通りだが、カードで立て替えた場合は現金がまだ出ていないため、残高から抜けていない。「立て替えた ＝ 現金が出た」と決め打ちできない。

そのため立替は実質資産の計算から外し、**「相手から返ってくる予定の額」として別枠に表示する**ことにした。把握したいという要求そのものは残っているが、残高と足し引きする形では正しく表せない。

### 1.2 目的

- 確定支出を加味した **実質的な資産額** を一目で把握できるようにする
- 貸し借りの未回収額を **実質資産とは別の参考値** として把握できるようにする
- 欲しいもの・やりたいこと・将来の目標を一元管理し、**目標までの不足額** を把握できるようにする

### 1.3 副次的な目的（開発上）

- ドメインモデリング、レイヤードアーキテクチャ、テスト設計の実践の場とする
- 生成コードやライブラリ実装のコードリードを通じて理解を深める

上記のため、機能の豊富さより **設計の筋の良さ** を優先する。

## 2. スコープ

### 2.1 対象

- 保有資産（現金・預金）の管理
- 立替金の管理と回収記録
- 支払い確定済みの予定支出の管理
- 欲しいもの・やりたいこと・目標の管理と不足額の算出
- 上記を統合したダッシュボード表示

### 2.2 対象外（今回は作らない）

| 項目 | 理由 |
| --- | --- |
| 銀行API連携による残高自動取得 | 個人開発では契約面で現実的でない |
| レシート読み取り・OCR | 目的に対して不要 |
| 日々の生活費の記録（食費、光熱費等の家計簿） | 既存アプリの領域。目的外 |
| 複数ユーザー・共有機能 | 個人利用のため |
| 外貨・為替 | 日本円のみ扱う |
| 予算管理・支出分析レポート | 目的外 |
| 確定支出の分割払い | 内金・残金のような分割は扱わない。金額は一括で扱う |
| 投資資産の実質資産への算入 | 別枠の参考値として表示するのみ（3章参照） |
| 立替金の実質資産への算入 | 別枠の参考値として表示するのみ（1.1 で変更。3章参照） |

### 2.3 前提

- 残高の更新は **手動入力** とする。入力頻度は月1回程度で成立する設計にする
- 扱う通貨は日本円のみ。金額は円単位の整数で扱う

## 3. 用語定義

このアプリの中核となる概念。実装のクラス名・テーブル名もこれに揃える。

| 用語 | 定義 |
| --- | --- |
| **口座 (Account)** | 現金・預金口座など、資産を保持する入れ物 |
| **口座残高 (Balance)** | 口座が保持している金額。手動更新される |
| **立替金 (Lending)** | 他人のために支払い、まだ回収していない金額。自分にとっての債権。**実質資産には含めない**（1.1 で変更） |
| **確定支出 (Commitment)** | 支払うと確定しているが、まだ支払っていない金額。自分にとっての債務 |
| **実質資産 (Net Asset)** | 現金・預金の残高合計 − 未払いの確定支出。**投資資産と立替金は含めない** |
| **投資資産 (Investment)** | 証券口座等の評価額。実質資産とは別枠の参考値として表示する |
| **未回収 (Outstanding)** | 立替金のうちまだ回収していない額。`amount − collected_amount`。実質資産とは別枠の参考値として表示する |
| **ウィッシュ (Wish)** | 欲しいもの・やりたいこと・将来の目標。金額の見積を持つ |
| **不足額 (Shortfall)** | ウィッシュの目標金額 − 実質資産。マイナスなら達成可能 |
| **月次収支 (MonthlyBalance)** | 月ごとに都度入力する収入と支出。ここでの支出は生活費等を指し、ウィッシュ由来の支出は含めない |
| **月間余剰 (Surplus)** | 月次収入 − 月次支出。プラスならその月は黒字、マイナスなら赤字 |

### 3.1 中核となる計算式

```
実質資産 = Σ(現金・預金の残高) − Σ(未払いの確定支出)

未回収の立替 = Σ(立替金の amount − collected_amount)   ← 実質資産には足さない

不足額(ウィッシュ) = ウィッシュの金額 − 実質資産

月間余剰(当月) = 月次収入 − 月次支出

平均月間余剰 = 直近3ヶ月の月間余剰の平均（データが3ヶ月未満の場合は存在する月の平均）

到達見込み月数(ウィッシュ) = 不足額 ÷ 平均月間余剰
```

この式が本アプリの存在理由であり、ドメイン層の純粋関数として実装する。

**算出上の取り決め**

- 不足額は**ウィッシュごとに独立して**算出する。複数ウィッシュの合計金額との比較は行わない（「Aも買えるしBも買える」と表示されるが、それを許容する）
- 到達見込み月数は単月ではなく**直近3ヶ月の平均**を用いる。単月だとボーナスや大きな出費で予測が大きく振れるため
- 平均月間余剰が0以下の場合、到達見込み月数は算出せず「算出不可」と表示する
- 月次収支のデータが1ヶ月分もない場合も「算出不可」とする
- 投資資産は上記いずれの式にも登場しない。ダッシュボードに参考値として別途表示するのみ
- **立替金も同様に、実質資産・不足額・到達見込みのいずれの式にも登場しない。** ダッシュボードに参考値として別途表示するのみ（1.1 で変更）。立替の登録・回収で口座残高は動かない
- 月次支出予定とウィッシュ由来の確定支出は**二重計上しない**。生活費等は月次支出予定に、ライブや旅行などはウィッシュとして登録し、両方に同じ支出を入れない

## 4. ドメインモデル

### 4.1 エンティティ一覧

#### Account（口座）

| 属性 | 型 | 備考 |
| --- | --- | --- |
| id | ID | |
| name | 文字列 | 「メイン銀行」「現金」「証券口座」など |
| kind | 列挙 | **現金預金 / 投資**。実質資産に算入するのは現金預金のみ |
| balance | Money | 現在残高（投資の場合は評価額） |
| updated_at | 日時 | 最終更新日。古いと警告表示する材料にする |

#### Lending（立替）

| 属性 | 型 | 備考 |
| --- | --- | --- |
| id | ID | |
| counterparty | 文字列 | 相手の名前 |
| amount | Money | 立て替えた総額 |
| collected_amount | Money | 回収済み金額。部分回収に対応 |
| description | 文字列 | 名目（「◯◯のライブチケット代」など） |
| occurred_on | 日付 | 発生日 |
| status | 列挙 | 未回収 / 一部回収 / 回収済 |

`amount − collected_amount` が未回収残高。**実質資産には加算しない**（1.1 で変更）。ダッシュボードに参考値として別枠で表示する。

#### Wish（ウィッシュ）

欲しいもの・やりたいこと・目標を統合して扱う。**ライブや旅行も、確定前はウィッシュとして登録される。**

| 属性 | 型 | 備考 |
| --- | --- | --- |
| id | ID | |
| title | 文字列 | |
| amount | Money | 金額。検討中は見積、確定後は確定額 |
| category | 列挙 | もの / 体験 / 目標 |
| priority | 整数 | 表示順 |
| deadline | 日付? | 任意。ライブ日程など |
| status | 列挙 | 検討中 / 確定 / 完了 / 見送り |

#### Transaction（取引）

残高の変動を記録する。残高の補正・履歴確認に用いる。

| 属性 | 型 | 備考 |
| --- | --- | --- |
| id | ID | |
| account_id | ID | |
| amount | Money | 符号付き |
| kind | 列挙 | 立替発生 / 立替回収 / ウィッシュ支払 / 残高調整 |
| ref_id | ID? | 関連する Lending / Wish |
| occurred_on | 日付 | |

#### MonthlyBalance（月次収支）

月ごとの収入と支出を都度入力する。その月が黒字だったか赤字だったかの記録であり、同時に到達見込み月数の算出根拠にもなる。

| 属性 | 型 | 備考 |
| --- | --- | --- |
| id | ID | |
| year_month | 年月 | 対象月。一意 |
| income | Money | その月の収入 |
| expense | Money | その月の支出（生活費等。ウィッシュ由来の支出は含めない） |

`income − expense` が月間余剰。プラスなら黒字、マイナスなら赤字として表示する。既定値は設けず、月ごとに都度入力する。

過去月の記録がそのまま将来予測の根拠になる構造のため、予定値と実績値を別々に持つことはしない。

### 4.2 状態遷移

**Wish の状態遷移** が本アプリで最も重要なルール。

```
  ┌─────────┐  買うと決めた       ┌────────┐  支払った   ┌────────┐
  │ 検討中  │ ─────────────────▶ │  確定  │ ──────────▶│  完了  │
  └─────────┘  チケットを取った   └────────┘             └────────┘
       │                              │
       │ やめた                        │ キャンセル
       ▼                              ▼
  ┌─────────┐                    ┌─────────┐
  │ 見送り  │                    │ 見送り  │
  └─────────┘                    └─────────┘
```

各状態が実質資産に与える影響：

| 状態 | 実質資産への影響 | 説明 |
| --- | --- | --- |
| 検討中 | なし | まだ自分の意思決定に入っていない |
| **確定** | **マイナス（確定支出として控除）** | 払うと決めた時点で自分の金ではない |
| 完了 | なし（口座残高が実際に減る） | 支払い時に Transaction が発生 |
| 見送り | なし | |

「確定」に入った瞬間から実質資産から差し引かれる、というのが 1.1 で挙げた課題2への回答。ライブや旅行を別エンティティにせず Wish の状態として扱うのは、両者のライフサイクルが同一のため。

**Lending の状態遷移**

```
未回収 ─(一部回収)─▶ 一部回収 ─(残額回収)─▶ 回収済
   └────────────(全額回収)──────────────────┘
```

## 6. 非機能要件

| 分類 | 要件 |
| --- | --- |
| 利用者 | 単一ユーザー。ただし複数端末（スマホ・タブレット・PC）のブラウザから利用する |
| 認証 | 単一ユーザー向けの簡易な認証を設ける。資産額を扱うため無認証は避ける |
| データ保管 | サーバー側のDBに保管し、端末間で同期する |
| オフライン対応 | 初期スコープ外。通信前提とする |
| 性能 | データ件数は年間数百件規模を想定。特別な最適化は不要 |
| 可用性 | 個人利用のため停止許容。SLA は定めない |
| テスト | 実質資産・不足額の計算ロジックは外部依存を持たない純粋関数とし、ユニットテストを必須とする。あわせて、**型チェック・lint・ユニットテスト・E2E が単一コマンドで完走すること**を front の要件とする（7.2 参照） |
| セキュリティ | 通信はHTTPS。認証情報はブラウザの `localStorage` に保管する。単一ユーザー・自分の端末のみという前提のもとで許容する |
| **コスト** | **月額0円で運用する。各サービスの無料枠を超える構成は採用しない。予算アラートの設定を必須とする** |
| インフラ管理 | 構成はリポジトリ内のファイル（`wrangler.jsonc` / `migrations/`）で管理し、コンソールでの手動設定に依存しない |

## 7. 技術構成

> **2026-07 に変更。** 当初は Go + PostgreSQL + Cloud Run + Terraform を採用していたが、「クレジットカードを登録しない」という制約が加わったため全面的に見直した。GCP は無料枠を使うだけでも請求先アカウント（＝カード登録）が必須のため。経緯と却下した選択肢は `docs/migration-cloudflare.md` にある。**要件（1〜6章）は一切変えていない。**

| 層 | 技術 | 選定理由 |
| --- | --- | --- |
| フロント | Vite + React + TypeScript（SPA） | 静的ビルドのみで完結する。Playwright / Vitest がそのまま噛み合う（7.2 参照） |
| バックエンド | TypeScript（Cloudflare Workers） | カード登録なしで月額0円。コールドスタートが無い |
| DB | Cloudflare D1（SQLite） | bindings で渡るため接続文字列もプールも無い。無料枠が単一ユーザーの規模に対して過剰 |
| クエリ | 生の `db.prepare()` + 手書きの行型 | SQL を自分で書く。ORM もクエリビルダも挟まない |
| HTTP ルータ | Hono | `app.request()` でハンドラを HTTP サーバー無しに単体テストできる |
| 配信方式 | 同一 Worker から静的アセットとして配信 | front と API が同一オリジンになり CORS が消える。静的アセットは無料枠を消費しない |
| デプロイ | `wrangler deploy` | 対象が1つ。front と API のデプロイがズレて壊れる事故が構造的に起きない |
| リポジトリ | モノレポ | front / worker を一元管理 |

### 7.1 リポジトリ構成

```
.
├── wrangler.jsonc          Worker 定義。D1 binding、静的アセット
├── migrations/             D1 のスキーマ
├── worker/                 TypeScript（domain / usecase / adapter / infra）
├── front/                  Vite + React + TypeScript
├── .github/workflows/      CI（変更ディレクトリ単位で実行）
└── docs/
```

CI は変更のあったディレクトリのみを対象に実行する（paths フィルタ）。front を触っただけで worker のテストが走る、あるいはその逆を避ける。front の E2E はブラウザを起動するぶん実行時間が長いため、無駄打ちを避ける意味はここでも残る。

**IaC は持たない。** 構成は `wrangler.jsonc` と `migrations/` がリポジトリ内で表現しており、コンソールでの手動設定に依存する部分は「サブドメインの登録」と「secret の登録」の2つだけ。Terraform の Cloudflare provider は存在するが、Workers は `wrangler` が正道であり、IaC の学習は今回の優先事項から外れている。

### 7.2 配信方式と、front を Web SPA とする理由

Vite でビルドした静的ファイルを、無料枠のあるホスティング（Cloudflare Pages 等）に置く。ホスティング先は front に着手する段階で確定させる。**静的ビルドしか出さない構成にしておけば、置き場所の決定を最後まで遅らせられる**ため、Next.js のようにサーバーを要するか static export の制約が付く選択肢は採らない。

スマートフォンからは、ブラウザで開くか PWA としてホーム画面に追加して使う。PWA 化は `vite-plugin-pwa` で manifest と Service Worker を足すだけで足り、後付けできるため初期スコープには含めない。App Store / Google Play には公開しない（2.2 参照）。

#### なぜ Expo / React Native をやめたか

当初は Expo Go + EAS Update を採用していた（既存の習熟を理由とする選定）。これを Web SPA に切り替える。理由は開発体制であって、好みではない。

**このプロジェクトは AI エージェントにループを回させる前提で進める。ループの成否は、エージェント自身が到達判定に使える検証手段があるかどうかで決まる。** 押し返してくるものが何もないループは、エージェントが自分の出力に自分で同意しているだけになる。

React Native では、エージェントが「画面が意図どおり描画されているか」を人手を介さずに確かめる手段が事実上ない。Web であれば Playwright が実際にブラウザを動かし、失敗を読み、直し、再実行できる。ここが埋まると、front の検証が次の一本のコマンドに収まる。

```json
"check": "npm run typecheck && npm run lint && npm run test && npm run e2e"
```

`npm run check` が通ることを、そのままループの停止条件として渡せる。Expo のままではこの最後の一段が埋まらない。

#### 切り替えの影響範囲

| | 内容 |
| --- | --- |
| 影響なし | 本要件定義書の1〜6章、DDL、ドメイン層、API 設計、詳細設計書。**`server/` は一行も変わらない** |
| 変更あり | 本章（技術構成）、非機能要件のセキュリティ・利用者、CI の front ジョブ、`CLAUDE.md`、`SETUP.md` |
| 失うもの | React Native の学習機会。ただし副次的な目的（1.3）の主眼は Go 側のアーキテクチャであるため、実害は無いと判断した |
| 弱くなる点 | F-12（残高更新リマインド）のプッシュ通知。優先度Cのため現時点では許容する |

front を丸ごと入れ替えても `server/` が無傷で済むのは偶然ではなく、レイヤ境界を引いた結果である。この切り替え自体が、境界の引き方が妥当だったことの検証になっている。

### 7.3 パッケージ構成（案）

```
worker/src/
  index.ts               依存の組み立て（DIは手書き）とエントリポイント
  domain/                エンティティ、値オブジェクト、ドメインサービス
                         → 外部依存ゼロ。実質資産の計算はここ
  usecase/               アプリケーションサービス
                         → domain と repository インターフェースのみに依存
  adapter/
    handler/             HTTPハンドラ
    repository/          リポジトリのDB実装
  infra/                 設定読み込み
```

### 7.4 設計上の約束

- 金額は裸の数値で扱わず `Money` 型を定義し、加減算を関数として持たせる
- 状態遷移のルールは Wish / Lending エンティティのメソッドに置く。usecase 層に散らさない
- DIコンテナは使わず `index.ts` で手動組み立てし、依存の向きを可視化する

### 7.5 コスト暴発防止

**Cloudflare の Free プランは、無料枠を超えると課金ではなく停止する。** これが月額0円を担保する仕組みそのものになっている。

> If you exceed any one of these limits, further operations of that type will fail with an error.
> （Workers の料金ドキュメント）

> When your account hits the daily read and/or write limits, you will not be able to run queries against D1.

Cloud Run を採用していた当時は、超過が課金に化ける設計だったため `max_instance_count` で天井を明示する必要があった。**Cloudflare では超過が停止に化けるため、天井を自分で設定する必要が無い。** 同じ種類の事故が構造的に起きない。

| 無料枠 | 上限 | このアプリの規模 |
| --- | --- | --- |
| Workers リクエスト | 10万/日 | API 呼び出しは多くても1日数百回。静的アセットは枠を消費しない |
| D1 行読み取り | 500万/日 | 全件取得しても年間数百件 |
| D1 行書き込み | 10万/日 | 1日数件 |
| D1 ストレージ | 5GB | 到達しない |

したがって、守るべきことは以下に尽きる。

- **有料プラン（Workers Paid）に切り替えない。** 既定は Free で、明示的に申し込まない限り Free のまま
- **無料枠を持たない機能を導入しない**（`CLAUDE.md`「やらないこと」参照）
- **独自ドメインを買わない。** `*.workers.dev` のサブドメインは無料

**カード登録は不要。** アカウント作成時にも求められない。

## 9. 決定事項と残論点

### 9.1 決定済み

| # | 論点 | 決定 |
| --- | --- | --- |
| 1 | 証券口座・投資資産の扱い | 実質資産には含めず、別枠の参考値として表示する |
| 2 | 不足額の算出方法 | 実質資産との単純差分とする |
| 3 | 複数ウィッシュの扱い | ウィッシュごとに独立して算出する。合計との比較は行わない |
| 4 | 確定支出の分割払い | 対応しない。スコープ外 |
| 5 | 立替の相手管理 | 文字列で保持する。Person エンティティへの正規化は行わない |
| 6 | 収入の扱い | 月次収支（収入・支出予定）を登録し、到達見込み月数を算出する |
| 7 | Cloud Run のリージョン（**#14 により失効**） | **us-central1（アイオワ）を採用。** コンピュートの無料枠はリージョンを問わず効くが、egress の無料枠1GiBが北米限定のため、厳密に0円とするには北米が必要。レイテンシ増は利用頻度から許容 |
| 8 | 実行環境の再検討（Render 等）（**#14 により失効**） | **Cloud Run を継続。** Render は導入が容易だが、(1) スリープ回避に外部監視サービスで常時ping する運用は無料枠750時間をほぼ使い切る上に公式サポート外、(2) コールドスタートが約1分、(3) IaC を書かない手軽さが Terraform 学習の目的と衝突する、ため不採用 |
| 9 | 月次支出の粒度 | **月ごとに1つの金額を都度入力する方式で確定。** 項目別の内訳は持たない（家計簿化を避けるため）。あわせて各月の黒字／赤字を一覧表示する |
| 10 | front の技術（Expo 継続か Web か） | **Expo / React Native を取りやめ、Vite + React + TypeScript の Web SPA に変更。** 開発を AI エージェントのループで進めるにあたり、エージェントが自力で画面の正しさを判定できる手段が要る。React Native にはそれが無く、Web なら Playwright で埋まる。`npm run check`（型チェック + lint + ユニット + E2E）が丸ごとループの停止条件になることを重視した。`server/` への影響はゼロ。判断時点で front はテンプレートのままであり、乗り換え費用が実質ゼロだったことも決め手（7.2 参照） |
| 11 | ネイティブアプリとしての配布 | **行わない。** スマートフォンでは PWA としてホーム画面に追加する。`vite-plugin-pwa` による後付けで足りるため、初期スコープには含めない |
| 12 | front の linter | **oxlint を採用（eslint ではなく）。** Vite の公式テンプレートが既定で同梱しており設定が要らないこと、eslint より桁違いに速いことによる。ループでは lint が1周ごとに走るため、ここの実行時間がそのまま周回速度に効く。型を要する検査は `tsc` が担うので、eslint の型情報つきルールを失う影響は小さいと判断した |
| 14 | 実行環境の再々検討（**#7・#8 を失効させる**） | **Cloud Run / Neon / Terraform を取りやめ、Cloudflare Workers + D1 に変更。** 判断の前提が変わったため。「クレジットカードを登録しない」という制約が加わり、GCP は無料枠を使うだけでも請求先アカウントが必須なので落ちた。カード不要 × 月額0円 × Go で探すと Render Free 程度しか残らず、15分でスリープし復帰に30〜60秒かかる。**言語の縛りを外した瞬間に、この制約群を全部満たす構成が現れた。** 実装言語は Go から TypeScript へ。要件（1〜6章）と設計（データモデル・レイヤ構成・API・用語）は変えていない。経緯と実測は `docs/migration-cloudflare.md` |
| 15 | 認証方式を維持するか | **固定トークンを維持する。** アカウント登録式にしたいという要望が出たが、(1) Cloudflare Access は `*.workers.dev` に適用できず独自ドメインが要る（月額0円に反する）、(2) 動機が「長いトークンの保管が面倒」だけなら合言葉に変えるだけで済む、(3) マルチユーザー化は「やらないこと」に踏み込む。検討の前提は `docs/design.md` 4.5 に残した |
| 13 | リポジトリの公開範囲 | **public にする。** GitHub Actions の実行時間が無制限で無料になるため。private の Free プランは月2,000分で、ジョブごとに分単位で切り上げられる。エージェントにループを回させる以上 CI の実行回数が読めず、分数を気にして検証を削るのは本末転倒。副次的に secret scanning と push protection が無料で使える。代償として秘密情報の事故が即座に致命的になるため、push protection の有効化を必須とし、コミットの Author には GitHub の noreply アドレスを使う（`SETUP.md` 2章） |

### 9.2 残論点

| # | 論点 | 状況 |
| --- | --- | --- |
| A | `infra/` を別リポジトリに分けるか | **論点ごと消滅（#14）。** Terraform を採らないため `infra/` 自体が無くなった。公開されて困る構成情報は残っておらず、`wrangler.jsonc` に入る `database_id` は単体では何も開けない |
| B | CI からの自動デプロイ | **導入済み。** `main` へのマージで、チェック → front のビルド → D1 のマイグレーション → デプロイ → 疎通確認、の順に走る。マイグレーションを自動化したのは、順序（スキーマ→コード）を機械に保証させるため。壊れた DDL が本番に当たる危険は残るが、D1 の Time Travel（30日、無料）で巻き戻せる |
