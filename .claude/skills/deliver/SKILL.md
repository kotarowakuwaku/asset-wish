# 要望から PR まで

**目的は「動くもの」ではなく「制約を守ったまま動くもの」を出すこと。** 手順を飛ばすと、後から文書が腐り、不変条件が破れる。

前提として `CLAUDE.md` の不変条件と、`docs/` の4文書を読んでいること。

---

## 1. 論点を洗う（コードを書く前）

**要望をそのまま実装しない。** まず、この要望が触る範囲を確かめる。

1. **`docs/decisions.md` を読む。** 同じ論点が過去に決着していないか。**却下済みの案を蒸し返さない**
2. **`docs/domain.md` 7章「やらないこと」に触れていないか。** 触れているなら、実装する前にそれを伝える
3. 影響するレイヤを数える（domain / usecase / adapter / front / migrations / docs）
4. **既存の不変条件と衝突しないか。** 衝突するなら、不変条件のほうを変える提案として出す（勝手に破らない）

### 分岐したら必ず聞く

**ユーザーが自分で考えるべき設計判断を、勝手に決めて先に進まない。**

聞くべきものと、自分で決めてよいものの線引き：

| 聞く | 自分で決める |
| --- | --- |
| データの持ち方が変わる（列の追加、型の選択） | 変数名、ファイルの分割 |
| 既存データの扱いが変わる（消す・移す・残す） | テストケースの並べ方 |
| API の形が変わる（経路、受け取る項目） | コメントの書き方 |
| 挙動の選択肢が2つ以上ある（削除で残高を戻すか、など） | 慣例に沿った書き方 |
| 不変条件に触れる | |

**聞くときは選択肢とトレードオフを示す。** 「どうしますか？」だけでは答えられない。推奨案には理由を添える。

### 決まったことは、その場で記録する準備をする

**決定の理由は、実装が終わるころには思い出せない。** 論点を洗った時点でメモしておき、`docs/decisions.md` に書く材料にする。**却下した案とその理由が、後で一番効く。**

---

## 2. ブランチを切る

```bash
git checkout -b <prefix>/<短い説明>
```

prefix は `feat` / `fix` / `refactor` / `docs` / `chore`（`docs/architecture.md` 9章）。迷ったら `feat`。

**未マージの PR の上に積む場合は、ベースをそのブランチにする。** そうしないと差分に前の PR が丸ごと混ざる。

---

## 3. 実装する

**1周で触る範囲は原則1レイヤまで。** 範囲が広いほど、落ちたときに原因を特定できなくなる。

推奨する順番（下の層から）：

```
migrations → domain → usecase/port → adapter/repository → adapter/handler → front → docs
```

理由は、**下から積むと型チェックが常に「次に何を直すか」を教えてくれる**ため。上から書くと、下が無いので型が通らず、まとめて書くことになる。

各レイヤを終えたらチェックを回す（次節）。

### 実装中に守ること

- **domain にロジックを寄せる。** 判断（遷移の可否、削除の可否、集計に足すか）はエンティティか純粋関数に置く
- **書き込みは usecase が組み立てる。** 複数行にまたがるなら `WriteOperation` の配列にして `writeAll` に渡す
- **テストを同時に書く。** domain は例外なく必須。あとで書くと、実装に合わせたテストになる
- **コメントには「なぜ」を書く。** 「何を」しているかはコードが語る。**採らなかった選択肢を書き残すと、次に読む人が同じ検討をせずに済む**

---

## 4. チェックを回す

`CLAUDE.md`「ループ協議」に従う。**チェックが緑になっていない状態を「完了」と呼ばない。**

| 触った場所 | 走らせるもの |
| --- | --- |
| `worker/` | ルートで `npm run check` |
| `migrations/` | 上記に加えて `npm run migrate:local` |
| `front/` | `cd front && npm run check` |

- 落ちたら、出力を最後まで読み、**原因を1文で言語化してから**直す
- 周回は最大5回。同じエラーが2周続いたら `fixer` を呼ぶ
- **テストの削除・スキップ・アサーションの緩和で緑にしない**

---

## 5. 自己レビューを回す

**`/architecture-review` を必ず使う。** 自分が書いたコードでも、同じ厳しさで見る。

レビューで出た指摘は、**PR を出す前に直す**（重大・要修正のもの）。直したら、その内容を PR 本文の「自己レビューで直した点」に書く。**何を見落としていたかが残ると、次に同じ見落としをしにくくなる。**

指摘がゼロなら、無理に作らない。

---

## 6. 文書を更新する

**これが一番忘れられる。** コードだけ直して文書を放置すると、次に読む人（自分を含む）が間違える。

**どの変更でどの文書を更新するかは、`/architecture-review` の6章に表がある。** ここに同じ表を置くと、片方だけ古くなる。

**同じ事実を2箇所に書かない。** 書いた瞬間は正しくても、片方だけ更新されて必ず腐る。

`docs/decisions.md` に書くのは、**決定・理由・却下した案**の3つ。「何をしたか」は git log にある。ここに書くのは「なぜそうしたか」。

更新したら `npm run constraints` をもう一度走らせる（消した文書への参照が残っていないか）。

---

## 7. コミットして PR を出す

### コミット

`prefix: 要約` の形。本文には**決定と理由**を書く。

```
feat: 定期入出金（給料・家賃）を足す

毎月同じ額が動くものを都度打つのは手間で、打ち忘れると残高がずれる。

- 適用は自動では起きない。押したときだけ残高が動く
- 残高・履歴・適用済み年月を1回の batch にまとめる（不変条件10）

経緯は docs/decisions.md の 2.5。
```

### PR 本文に必ず入れるもの

1. **何ができるようになるか**（利用者の言葉で）
2. **決めたこと**（表で。採った案と却下した案を並べる）
3. **不変条件との対応**（どの不変条件をどう守ったか）
4. **マイグレーションの有無**（あるなら、作り直しかどうか）
5. **検証の証拠**（テストの件数と、CI が通ったこと）
6. **自己レビューで直した点**
7. **残した論点**（意図的に手をつけなかったこと）

### 出したあと

```bash
# pending が消えるまで待ってから結果を見る
until [ "$(gh pr checks <番号> | grep -c pending)" = "0" ]; do sleep 15; done
gh pr checks <番号>
```

**CI が赤いまま「出しました」と言わない。**

### PR を出したあとに追加で直すとき

**まず、その PR がまだ open か確認する。**

```bash
gh pr view <番号> --json state --jq .state
```

マージ済みなら、ブランチに push しても**その PR には乗らない**（head が固定される）。`git push` は成功し、`git ls-remote` にも新しいコミットが見えるので、**成功したように見えて実際は取りこぼす。**

マージ済みだった場合は、main から切り直して別の PR にする。

```bash
git checkout main && git pull
git checkout -b <prefix>/<説明>
git cherry-pick <取りこぼしたコミット>
```

**「push が反映されない」と GitHub 側を疑う前に、PR の状態を見ること。** 実際にこれで時間を溶かした。

---

## やらないこと

- 論点を確認せずに実装を始める（分岐がある場合）
- チェックの出力を示さずに「完了」と報告する
- 文書を更新せずに PR を出す
- `main` に直接コミットする
- 本番データを触る操作を、確認なしに実行する
