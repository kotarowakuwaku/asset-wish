# アーキテクチャレビュー

このリポジトリ固有のレビュー観点。汎用的なコードレビュー（変数名、可読性など）より**先に**、以下を確認する。

前提として `CLAUDE.md` の「絶対に守る不変条件」と `docs/design.md` を参照する。矛盾があれば設計書が正。

## 手順

1. 変更されたファイルがどの層に属するか特定する（domain / usecase / adapter / infra / front）
2. 層ごとのチェック項目を上から順に確認する
3. ドメインルールのチェックを行う（層に関係なく必ず）
4. テストの有無を確認する
5. 指摘を重大度別に整理して報告する

---

## 1. レイヤ境界

### `internal/domain` に変更がある場合

- [ ] import に外部依存が入っていないか（`database/sql`、`net/http`、HTTP フレームワーク、sqlc 生成パッケージ、`internal/adapter`、`internal/infra`）
- [ ] `context.Context` を引数に取る関数が増えていないか。ドメインの計算に context は不要
- [ ] DB やネットワークを触らずにテストできる状態を保っているか
- [ ] sqlc が生成した構造体がドメインの型として使われていないか

**depguard が落ちた場合、`.golangci.yml` を緩めて通すことは絶対にしない。** 設計のほうを直す。緩める必要があると判断した場合は、実装を進める前にユーザーに相談する。

### `internal/usecase` に変更がある場合

- [ ] 状態遷移の可否を判定する条件分岐（`if wish.Status == ...`）を書いていないか。それは domain のメソッドの責務
- [ ] リポジトリのインターフェースが `usecase` パッケージに定義されているか（`adapter` 側ではなく）
- [ ] 複数テーブルを更新する操作でトランザクションが張られているか
- [ ] 実質資産・不足額・到達見込みの計算式をここに再実装していないか。`domain` の関数を呼ぶこと

### `internal/adapter/repository` に変更がある場合

- [ ] sqlc 生成構造体とドメインエンティティの相互変換が、この層で行われているか
- [ ] SQL に計算ロジック（実質資産の集計など）が混入していないか。データを取ってくるだけに留めているか
- [ ] N+1 になっていないか

### `internal/adapter/handler` に変更がある場合

- [ ] ドメインエラーが 422、形式エラーが 400 にマッピングされているか
- [ ] ビジネスロジックが入り込んでいないか。JSON 変換とエラー変換に徹しているか
- [ ] 状態遷移が `PATCH {status: ...}` ではなく専用エンドポイント（`/commit`、`/pay`、`/drop`）になっているか

---

## 2. ドメインルール

**ここが最重要。** アプリの存在意義に直結する。

- [ ] 実質資産の計算に `kind = 'investment'` の口座が混入していないか
- [ ] 実質資産から控除されるウィッシュが `status = 'committed'` のみに限定されているか
- [ ] 月次支出とウィッシュ由来の支出が二重計上される経路が生まれていないか（UI・API・集計のいずれでも）
- [ ] 立替の回収で、未回収残高を超える額が受け付けられていないか
- [ ] 終端状態（`done` / `dropped`）からの遷移が拒否されているか
- [ ] 平均月間余剰が 0 以下、またはデータ 0 件のとき、到達見込みが「算出不可」になっているか

## 3. 金額と型

- [ ] 金額が `domain.Money` 型で扱われているか。`int64` の裸の値が層をまたいでいないか
- [ ] 金額に浮動小数点が使われていないか
- [ ] JSON 上で金額が整数（円）になっているか。文字列化していないか

## 4. データベース

- [ ] 導出可能な値がカラムとして追加されていないか（立替の `status` など）
- [ ] CHECK 制約が抜けていないか（金額の符号、状態の列挙値、回収額の上限）
- [ ] マイグレーションが追記のみで、既存のマイグレーションファイルを書き換えていないか
- [ ] `sqlc generate` の結果がコミットされているか（`sqlc diff` で確認）

## 5. テスト

- [ ] domain の変更にテストが付いているか。**ここは例外なく必須**
- [ ] テーブル駆動になっているか
- [ ] 境界値が含まれているか（0円、余剰0、データ0件、データ3ヶ月未満）
- [ ] 異常系が含まれているか（不正な状態遷移、過回収）
- [ ] モックライブラリではなく手書きの fake を使っているか
- [ ] テストが実装の内部構造ではなく、外から見た振る舞いを検証しているか

## 6. 命名

- [ ] `docs/design.md` の用語と一致しているか

| 概念 | 使う名前 | 使わない名前 |
| --- | --- | --- |
| 実質資産 | `NetAsset` | `TotalAsset`、`RealAsset` |
| 月間余剰 | `Surplus` | `Balance`、`Diff` |
| 不足額 | `Shortfall` | `Remaining`、`Gap` |
| 未回収残高 | `Outstanding` | `Unpaid`、`Rest` |
| 確定支出 | `Commitment` | `Fixed`、`Planned` |

## 7. スコープ

- [ ] `CLAUDE.md` の「やらないこと」に踏み込んでいないか
- [ ] 有料サービス・有料プランを前提とした実装が入っていないか
- [ ] 秘密情報がハードコードされていないか

## 指摘の書き方

重大度を分けて報告する。全部を同じ重さで並べない。

**重大** — 不変条件の違反、ドメインルールの取りこぼし、レイヤ境界の破壊。修正するまで先に進まない。

**要修正** — テストの欠落、制約の抜け、命名の不一致。この作業の区切りまでに直す。

**提案** — 可読性、より素直な書き方。採否はユーザーが決める。

各指摘には**なぜそれが問題か**を1文添える。「規約だから」では学習にならない。何が壊れるのかを書く。

問題が見つからなかった場合は、無理に指摘を作らない。「確認した観点」と「問題なし」を短く報告する。

## やらないこと

- ユーザーに確認せずにリファクタリングを始める
- 指摘と同時に修正を適用する（指摘 → 合意 → 修正の順を守る）
- 設計書と異なる方針を、設計書を更新せずに実装に持ち込む
