# アーキテクチャレビュー

このリポジトリ固有のレビュー観点。汎用的なコードレビュー（変数名、可読性など）より**先に**、以下を確認する。

## 前提

| 参照先 | 何を見るか |
| --- | --- |
| `CLAUDE.md` | 絶対に守る不変条件（1〜17）。**最優先** |
| `docs/domain.md` | 用語・状態遷移・計算式。ドメインの正 |
| `docs/architecture.md` | レイヤの責務・原子性・命名・テスト。構造の正 |
| `docs/decisions.md` | 却下した選択肢。**「こうすればいいのでは」を書く前に読む** |

**文書と実装が食い違っていたら、それ自体が指摘対象。** どちらが正かは決め打ちせず、両方を挙げて確認を取る。

## 手順

0. **まず `npm run constraints` を走らせる。** 機械的に検出できるものはここで出る。人間が読むべき観点に集中するため、先に潰す
1. 変更されたファイルがどの層に属するか特定する（domain / usecase / adapter / infra / front）
2. 層ごとのチェック項目を上から順に確認する
3. ドメインルールのチェックを行う（層に関係なく必ず）
4. テストの有無を確認する
5. **文書の更新漏れを確認する**
6. 指摘を重大度別に整理して報告する

---

## 1. レイヤ境界

### `worker/src/domain` に変更がある場合

- [ ] import に外部依存が入っていないか（`hono` / `cloudflare:*` / `node:*` / 他の層）
- [ ] `Date` を値として保持していないか。`IsoDate` / `Instant` / `YearMonth` を使う。例外は `parseIsoDate` の検査だけ
- [ ] DB もネットワークも触らずにテストできる状態を保っているか
- [ ] D1 の行型（`AccountRow` など）がドメインの型として使われていないか

**oxlint が落ちた場合、`.oxlintrc.json` を緩めて通すことは絶対にしない。** 設計のほうを直す。緩める必要があると判断した場合は、実装を進める前にユーザーに相談する。

### `worker/src/usecase` に変更がある場合

- [ ] 状態遷移・削除可否の条件分岐（`if (wish.status === ...)`）を書いていないか。それは domain のメソッドの責務（不変条件6）
- [ ] リポジトリのインターフェースが `usecase` に定義されているか（`adapter` 側ではなく。不変条件9）
- [ ] 複数行にまたがる書き込みが1回の `writeAll` にまとまっているか（不変条件10）
- [ ] **同じ行への更新を2本並べていないか。** 2本目の `expected*` が1本目の適用後の値と食い違い、番人が必ず失敗する
- [ ] 実質資産・不足額・到達見込み・月次の集計をここに再実装していないか。`domain` の関数を呼ぶこと

### `worker/src/adapter/repository` に変更がある場合

- [ ] 行型とドメインエンティティの相互変換が、この層で行われているか（不変条件7）
- [ ] `restore` が `kind` / `status` / `category` / 年月を検証しているか（CHECK 制約をすり抜けた値の関門）
- [ ] SQL に計算・集計が混入していないか。データを取ってくるだけに留めているか（不変条件8）
- [ ] **更新の文が操作別に分かれているか。** 全カラムを上書きする文を足していないか（`docs/architecture.md` 4章）
- [ ] 新しいテーブルなら、リポジトリのテストがあるか（SQL と行型のズレ、CHECK 制約）

### `worker/src/adapter/handler` に変更がある場合

- [ ] ドメインエラーが 422、形式エラーが 400、競合が 409、不在が 404 に対応しているか（不変条件13）
- [ ] ビジネスロジックが入り込んでいないか。JSON 変換とエラー変換に徹しているか
- [ ] 状態遷移が `PATCH { status }` ではなく専用エンドポイントになっているか
- [ ] 受け付けるキーを明示しているか。**送れない項目を黙って無視していないか**
- [ ] レスポンスの形が front の型（`front/src/api/types.ts`）と一致しているか

### `front/` に変更がある場合

- [ ] 金額を計算していないか。サーバーが算出済みの値を並べるだけか（不変条件8）
- [ ] `fetch` を画面から直に呼んでいないか。`src/api/client.ts` に集約されているか
- [ ] 「算出不可」の `null` を 0 として表示していないか
- [ ] 基底 URL が空文字のままか（絶対 URL に戻すと CORS が復活する）

## 2. ドメインルール

**ここが最重要。** アプリの存在意義に直結する。

- [ ] 実質資産の計算に `kind = 'investment'` の口座が混入していないか（不変条件1）
- [ ] 実質資産から控除されるウィッシュが `status = 'committed'` のみに限定されているか（不変条件3）
- [ ] 同じ支出が二重計上される経路が生まれていないか（不変条件2）。**月次の集計に足すのは `adjustment` と `recurring_applied` だけ**
- [ ] 貸し借りが口座残高・取引履歴を触っていないか。未精算残高を超える精算が弾かれるか（不変条件4）
- [ ] 終端状態（`done` / `dropped`）からの遷移が拒否されているか
- [ ] 適用済み年月の巻き戻しが拒否されているか
- [ ] 「算出不可」が 0 ではなく `null` で表されているか

### 判断の軸を混ぜていないか

取引履歴には**別々の軸**がある。1つの述語で両方を判断していないか確認する。

| 軸 | 述語 | 対象 |
| --- | --- | --- |
| 消せるか | `isManualEntry()` | `adjustment` のみ |
| 月次に足すか | `countsTowardMonthlySummary()` | `adjustment` と `recurring_applied` |

## 3. 金額と型

- [ ] 金額が `Money` 型で扱われているか。裸の `number` が層をまたいでいないか（不変条件11）
- [ ] 金額に浮動小数点が使われていないか
- [ ] JSON 上で金額が整数（円）になっているか。文字列化していないか
- [ ] 符号の約束が守られているか（取引履歴と定期入出金は符号付きで、出るときが負）

---

## 4. データベース

- [ ] 導出可能な値がカラムとして追加されていないか（不変条件12）
- [ ] CHECK 制約が抜けていないか（金額の符号、状態の列挙値、精算額の上限、年月の形式）
- [ ] マイグレーションが追記のみで、既存のファイルを書き換えていないか
- [ ] **CHECK 制約を変えるならテーブルの作り直しになっているか**（SQLite は後から足せない）
- [ ] 新しいテーブルが `accounts` を参照するなら、`worker/test/db.ts` の `resetDb` に削除が足されているか

---

## 5. テスト

- [ ] domain の変更にテストが付いているか。**ここは例外なく必須**
- [ ] テーブル駆動になっているか
- [ ] 境界値が含まれているか（0円、余剰0、データ0件、月末の無い月、閏年）
- [ ] 異常系が含まれているか（不正な遷移、過精算、競合）
- [ ] 競合のテストが**実 D1** に対しても掛かっているか（`writer.test.ts`）
- [ ] モックライブラリではなく手書きの fake を使っているか
- [ ] テストが実装の内部構造ではなく、外から見た振る舞いを検証しているか
- [ ] **実データが混入していないか**（不変条件17。金額・口座名・人名はすべて架空のもの）

---

## 6. 文書の更新漏れ

**5本の仕様変更で、毎回ここが漏れた。** コードだけ直して文書を放置すると、次に読む人（自分を含む）が間違える。

変更の種類ごとに、更新すべき文書：

| 変更 | 更新する文書 |
| --- | --- |
| 用語・エンティティ・状態遷移・計算式 | `docs/domain.md` |
| レイヤの責務・原子性・命名・テスト方針 | `docs/architecture.md` |
| API 経路の追加・削除 | `docs/architecture.md` 11章 |
| 機能の追加・廃止 | `docs/requirements.md` |
| **何かを決めた／却下した** | `docs/decisions.md`（**理由と、却下した案を必ず書く**） |
| 不変条件そのもの | `CLAUDE.md`（**番号は変えない**） |

- [ ] 同じ事実が2箇所に書かれていないか。**書かれていたら、それは将来必ず片方が腐る**
- [ ] 消した経路・型・文書への参照が残っていないか

- [ ] 有料サービス・有料プランを前提とした実装が入っていないか（不変条件15・16）

## 指摘の書き方

重大度を分けて報告する。全部を同じ重さで並べない。

**重大** — 不変条件の違反、ドメインルールの取りこぼし、レイヤ境界の破壊。修正するまで先に進まない。

**要修正** — テストの欠落、制約の抜け、命名の不一致、文書の更新漏れ。この作業の区切りまでに直す。

**提案** — 可読性、より素直な書き方。採否はユーザーが決める。

各指摘には**なぜそれが問題か**を1文添える。「規約だから」では学習にならない。何が壊れるのかを書く。

**自分が書いたコードをレビューするときも、同じ厳しさで見る。** 「意図的にそうした」で流さず、その意図が文書のどこに書いてあるかを確認する。書いていなければ、それは文書の更新漏れ。

問題が見つからなかった場合は、無理に指摘を作らない。「確認した観点」と「問題なし」を短く報告する。

## やらないこと

- ユーザーに確認せずにリファクタリングを始める
- 指摘と同時に修正を適用する（指摘 → 合意 → 修正の順を守る）
- 文書を更新せずに実装だけ変える
- `docs/decisions.md` で却下済みの案を、理由を読まずに再提案する
